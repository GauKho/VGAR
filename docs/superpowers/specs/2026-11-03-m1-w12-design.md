## 1. T1: nối `signature_changed` (H3)

### 1.1. Hiện trạng

- `src/vgar/graph/impact.py:265`: `compute_impact` luôn ghi `signature_changed` là
  `{'available': False, 'reason': 'NOT_COMPUTED'}`.
- M2 đã có `check_api(before, after)` và `with_api_risk(report, analysis)` trong
  `src/vgar/repair/api_check.py:287, 356`. `with_api_risk` hiện chỉ được gọi trong
  `tests/m2/w1112/test_api_check.py`.
- `diff_to_nodes` (`impact.py:110`) đã gọi `_bind(parsed, root)`. Hàm này trả `(predicted, transport)`,
  trong đó `predicted[path]` là bytes của file sau patch, nhưng kết quả đang bị bỏ đi.

### 1.2. Thiết kế

Trong `analyze_patch_impact` (`impact.py:273`):

1. Đọc bytes baseline và tính `predicted` cho các file trong patch, **dùng cùng snapshot** với `diff_to_nodes`
   (không đọc đĩa lần hai sau khi đã kiểm snapshot).
2. Chỉ giữ file `.py`. `before = {path: baseline bytes}`, `after = {path: predicted bytes}`.
3. `analysis = check_api(before, after)`, rồi `report = with_api_risk(report, analysis)`.
4. Nếu patch không chạm file `.py` nào thì giữ nguyên `NOT_COMPUTED`.

Cách lấy `predicted` **(tôi chọn)**: tách phần thân của `diff_to_nodes` thành một hàm nội bộ trả thêm
`predicted` và `sources`; `diff_to_nodes` giữ nguyên chữ ký public và output. Không gọi `_bind` hai lần.

`compute_impact` không đổi. `callers_in_repo` không truyền (D2: chỉ để báo cáo, không phải điều kiện).

### 1.3. Ngữ nghĩa giữ nguyên

- Phạm vi so sánh chỉ là **các file trong patch**. Đây là giới hạn của `check_api` (`scope = static-python-public-api`).
- `check_api` trả `ERROR`/`NOT_RUN` (parse lỗi, scope rỗng) thì `with_api_risk` ghi `NOT_COMPUTED`. Không đổi
  enum `reason` của contract `ImpactReport`.
- Patch có `changed` rỗng: bốn feature kia vẫn là `NO_CHANGED_NODES`, còn `signature_changed` vẫn được đo
  nếu `check_api` đo được **(tôi chọn)**: đổi `__all__` hoặc chữ ký ở mức module vẫn là thay đổi API.

### 1.4. Ảnh hưởng tới thí nghiệm

`ImpactReport` đi vào feedback của các arm có graph và vào `solve --agent` (W10, `analyze_patch_impact`
qua graph MCP). Thêm một giá trị vào `risk.features` có thể làm đổi nội dung prompt lượt thử lại.

- Phải merge **trước** lượt chạy lại A1/A2 + A3 ở W12 ngày 1, để mọi arm trong batch dùng cùng code.
- Nếu không kịp: để T1 sau batch, ghi rõ trong `docs/m1_retrieval_method.md` và status rằng batch W12 chạy
  với `signature_changed = NOT_COMPUTED`.
- Hash config ranking đã đóng băng (`sha256:993f02c9…`) **không đổi**: retrieval chạy trước khi có patch,
  `public_api_risk` trong `retrieval.py` không đọc trường này.

## 2. T2: `bench_incremental.py` và bảng U1 (M1-W12-1)

### 2.1. Mục tiêu

Trả lời proposal §11.3: một lần cập nhật incremental nhanh hơn full rebuild bao nhiêu, và kết quả có đúng
không. **Không** nối incremental vào repair hay MCP (giữ quyết định của spec W11).

### 2.2. Giao diện

```
python scripts/bench_incremental.py --repo <checkout> --source-roots <r1,r2> \
    [--repeats 10] [--out results/m1/w12/u1/<timestamp>]
python scripts/bench_incremental.py --fixture [--repeats 3] --out <tmp>   # CI
```

- `--repo`: checkout của một dev task. Mặc định dùng **`pydata__xarray-4629`** **(tôi chọn)**: spec W11 đã
  ước lượng trên xarray (~0,4 s, nhanh hơn ~14 lần), nên số đo thật đối chiếu được.
- `--repeats`: mặc định 10, chặn trên 30 (yêu cầu "chạy lặp có giới hạn").
- Script **không bao giờ sửa checkout gốc**. Nó copy sang thư mục tạm và chỉ sửa bản copy.

### 2.3. Kịch bản

Ba kịch bản theo plan. Đích sửa được chọn **tất định** từ graph baseline **(tôi chọn)**: file `.py` trong
source root có nhiều node Function/Method nhất, lấy hàm public đầu tiên theo `(path, start_line)`. Đích đã
chọn được ghi vào output.

| Kịch bản | Thay đổi trên bản copy |
|---|---|
| `body_edit` | Chèn một câu lệnh vô hại (`_ = 0`) vào đầu thân hàm đích |
| `add_delete_file` | Thêm một module mới có một hàm gọi hàm đích; lần đo sau xóa module đó |
| `public_signature` | Thêm tham số có default vào hàm đích |

### 2.4. Quy trình đo cho mỗi kịch bản

1. **Cold:** `IncrementalGraphBuilder.build()` trên baseline, đo 3 lần, lấy median.
2. **Warm:** với mỗi lần lặp: khôi phục bản copy về baseline, build lại để có cache (không tính giờ), áp
   thay đổi, đo `update()`. Lấy `UpdateSummary` (thời gian từng phần, cache hit, node bị ảnh hưởng).
3. **Đúng/sai:** ở lần lặp đầu, so document đã chuẩn hóa với `PythonGraphBuilder(...).build()` mới trên cùng
   source (cùng cách so của `tests/test_incremental.py`: sắp node/edge theo id, bỏ `statistics.build_time_ms`).
   Không trùng thì ghi `match = false` và **vẫn xuất bảng**, không dừng.

### 2.5. Output

- `u1.json`: commit git, repo, revision, source roots, `RESOLVER_PROFILE`, máy (OS, CPU, Python), số lần
  lặp, đích đã chọn, toàn bộ mẫu thời gian thô, và kết quả từng kịch bản.
- `u1.md`: bảng U1 sinh **từ `u1.json`**, đúng cột của `w11_w12_remediation_plan.md` §4:
  Kịch bản · Cold build (s) · Warm update p50/p95 (s) · Speedup (cold median / warm p50) · File đổi ·
  Node bị ảnh hưởng · Cache hit · Trùng full rebuild.
- Dưới bảng có một dòng cố định: phần parse là O(Δ), phần link vẫn O(N); speedup đến từ việc không parse lại
  file không đổi (spec W11 §3, "độ phức tạp trung thực").

`results/` nằm ngoài Git như các tuần trước; đường dẫn run ghi vào `docs/status/m1.md`.

### 2.6. Test (`tests/test_bench_incremental.py`)

- Chạy `--fixture --repeats 2` trên repo dựng trong `tmp_path`: có đủ 3 kịch bản, `match = true` cả 3,
  `u1.md` được sinh từ `u1.json` (sửa json rồi sinh lại thì bảng đổi theo).
- Checkout gốc không bị sửa (so hash trước và sau).

## 3. T3: impact trên gold patch, bảng I1 (M1-X2, RQ3)

### 3.1. Câu hỏi

Với patch đúng (gold), vùng impact của graph có chứa các test cần sửa (FAIL_TO_PASS) nhiều hơn một baseline
chỉ dùng diff không, và vùng đó to cỡ nào? Bảng I1 là bảng **phụ**, chỉ chạy trên **dev**.

### 3.2. Dữ liệu

- Task: 25 task của `configs/m1/w10_dev_manifest.json` (tiền tố đã dùng ở W10). Hai task trong
  `configs/m3/w10_dev/tasks/EXCLUDED.md` vẫn nằm trong mẫu số, ghi lý do.
- Mỗi task: checkout ở base commit (`@data/repositories/{task_id}` trên máy GPU), `source_roots` từ
  `configs/m3/w10_dev/tasks/<task>.json`, gold patch và F2P từ parquet SWE-bench đã pin.
- Graph: build mới bằng `PythonGraphBuilder` với resolver static (cùng `RESOLVER_PROFILE` với W11).

### 3.3. Hai phương pháp

| Phương pháp | Vùng impact | Test trong vùng |
|---|---|---|
| **Chỉ dùng diff** | Các file trong gold patch | Mọi hàm test trong file test có tên khớp module bị sửa (`test_<module>.py`, `<module>_test.py`, `tests/**/test_<module>.py`) |
| **Graph** | `analyze_patch_impact(gold, max_hops=2, max_nodes=200)` (mặc định hiện tại) | Item có `kind == 'Test'` |

Gold patch được lọc **chỉ giữ file nằm trong inventory của graph** (bỏ file test, file thêm mới, file ngoài
source root), vì `diff_to_nodes` từ chối file ngoài inventory. Số hunk bị bỏ được ghi lại theo task.

### 3.4. Mẫu số và khớp tên test

- Nhiều test F2P **được thêm bởi test_patch** nên không có trong baseline; không phương pháp nào thấy được
  chúng. **(tôi chọn)** Recall tính trên **F2P có trong baseline**. Báo riêng: tổng F2P, số F2P có trong
  baseline, số task có 0 F2P đo được (vẫn nằm trong bảng, ghi `n/a`).
- Định dạng F2P khác nhau theo repo (pytest node id; Django `test_x (app.tests.Class)`; sympy chỉ tên hàm).
  Chuẩn hóa về `(file nếu có, Class nếu có, tên hàm)` và khớp với node Test. Mỗi task ghi cách khớp và số
  F2P không khớp được. Không khớp được thì **không** tính là miss của phương pháp, mà ghi vào cột riêng.

### 3.5. Cột bảng I1

Theo mẫu §4 của remediation plan, có điều chỉnh **(tôi chọn)**:

| Phương pháp | N task | F2P đo được | Recall F2P trong vùng | Median số test trong vùng | Median số node trong vùng | Recall file test của test_patch |
|---|---|---|---|---|---|---|

- Cột "Recall file gold" của mẫu bị thay bằng **"Recall file test của test_patch"**: file gold là đầu vào của cả
  hai phương pháp nên recall luôn bằng 100%, không có thông tin. Người review cần xác nhận cách hiểu này.
- Recall gộp kiểu micro (tổng F2P trúng / tổng F2P đo được), kèm macro theo task trong `i1.json`.

### 3.6. Giao diện và output

```
python scripts/measure_patch_impact.py --manifest configs/m1/w10_dev_manifest.json \
    --data-root <data> --parquet <pinned.parquet> --out results/m1/w12/i1/<timestamp>
```

- Script gọi `require_split(manifest, allowed=("dev",))` trước khi làm gì khác: **không chạy held-out**.
- Output: `i1.json` (từng task: số hunk bị bỏ, F2P thô, F2P chuẩn hóa, khớp/không khớp, vùng của hai phương
  pháp, lỗi nếu có) và `i1.md` sinh từ json.
- Task lỗi (build graph lỗi, patch không map được) vẫn nằm trong mẫu số với `status = ERROR` và lý do.

### 3.7. Test (`tests/test_measure_patch_impact.py`)

- Fixture repo nhỏ + gold patch + F2P giả: recall của hai phương pháp đúng như tính tay.
- Chuẩn hóa tên F2P cho 3 định dạng (pytest, Django, sympy).

## 4. T4: dry-run toàn chuỗi (M1-W12-2)

### 4.1. Mục tiêu

- **[Bổ sung, đã ghi trong plan W11–12]:** chạy cả chuỗi retrieval → runner (A0–A3) → harness → aggregate

### 4.2. Giao diện

`scripts/dry_run_heldout_chain.py`, chạy trong WSL trên máy GPU. Plan W11–12 gọi tên là `.sh`; spec này chọn
**Python** để test được phần chấm cổng (§4.5) mà không cần GPU hay Docker **(tôi chọn)**.

```
python scripts/dry_run_heldout_chain.py --template configs/m3/w10_dev_stage1.json --data-root ~/w9 \
    --parquet <parquet đã pin> --out results/m1/w12/dry_run/<timestamp> [--arms A0,A1,A2,A3]
```

Không có cờ `--mode`: runner không cho `generation = fake` trên task SWE-bench
(`src/vgar/evaluation/repair/manifest.py:84-85`), nên dry-run luôn dùng model thật và mode đọc từ config.

Các bước, mỗi bước là một lệnh đã có sẵn:

1. Kiểm tiền điều kiện: hash ranking hiện tại bằng hash đã đóng băng; `configs/m2/variants/A3.json` tồn tại
   nếu `--arms` có A3; manifest chỉ chứa task dev.
2. **Retrieval:** export lại bundle cho 2 task bằng ranking đã đóng băng (`export_w9_pilot_bundles.py`
   hoặc script export W10 tương đương). Bundle W10 cũ **không dùng lại** (lý do ở §4.8).
   Sau đó **sinh config thí nghiệm** từ bundle mới (§4.8).
3. **Runner:** `run_repair_experiment.py preflight`, rồi `run`.
4. **Harness:** `grade_repair_candidates.py --execute`.
5. **Aggregate:** `run_repair_experiment.py aggregate`.

Bước nào lỗi thì dừng, ghi bước lỗi và exit code.

### 4.3. Chọn task và config

- **2 task đầu tiên có trạng thái RUNNABLE ở W10**, theo thứ tự của `configs/m3/w10_dev_stage1.json`,
  chọn **trước khi chạy** **(tôi chọn)**: `astropy__astropy-13033` và `django__django-10914`. Cả hai không nằm
  trong danh sách EXCLUDED hay OVER_CAP của W10, và là 2 task đầu của manifest, nên bước export dùng được
  `--limit 2`.
- Config dry-run được **sinh ra** (§4.8) vào thư mục output của lần chạy, từ template
  `configs/m3/w10_dev_stage1.json` **(tôi chọn)**. Không commit một file config viết tay, vì hash bundle đổi
  mỗi lần export.
- Dùng Qwen thật (quy tắc của nhóm: số liệu và demo dùng model thật).
- **Người dùng tự khởi chạy** trên máy GPU (quy tắc nhóm); spec chỉ cung cấp lệnh.

### 4.4. Output

`dry_run.json`:
- commit git, mode, arm, task đã chọn;
- hash: config runner, từng `A*.json`, ranking, manifest, model revision (D12), prompt (nếu runner ghi);
- từng bước: lệnh đầy đủ, thời gian bắt đầu/kết thúc, exit code, đường dẫn output;
- **số ERROR hạ tầng** và danh sách.

`heldout_commands.md`: cùng các lệnh đó với manifest held-out để trống (`<HELDOUT_MANIFEST>`) và `--limit`
bỏ đi. File này **chỉ để chép vào protocol**, script không bao giờ chạy nó.

### 4.5. ERROR hạ tầng

**(tôi chọn)** Định nghĩa để chấm cổng:

- **Tính là ERROR hạ tầng:** bước nào exit khác 0; record runner có trạng thái `ERROR`; harness grade
  `ERROR`; Docker/image/RAM gate lỗi; collection timeout của môi trường.
- **Không tính:** kết cục của model (`PATCH_PARSE_ERROR`, `PATCH_APPLY_FAILED`, `UNRESOLVED`, `TIMEOUT` sinh
  patch, verifier từ chối). Đó là kết quả thí nghiệm, không phải lỗi hạ tầng.

**Cổng đạt** khi hai lần chạy liên tiếp đều có 0 ERROR hạ tầng. Lần 2 chạy ở một phiên máy khác
(theo parallel-split spec: lần 1 đầu cửa sổ GPU, lần 2 cuối). Kết quả ghi vào `docs/status/m1.md` → H7.

### 4.6. Khi A3 chưa có

Nếu `A3.json` chưa merge: chạy với `--arms A0,A1,A2`. `dry_run.json` ghi `gate = INCOMPLETE_A3_MISSING`;
cổng **không** tính là đạt. Script không tự bỏ A3 nếu không truyền `--arms`.

### 4.7. Test

- Orchestrator chạy với hàm chạy lệnh giả (không subprocess thật): đủ các bước theo thứ tự, có
  `dry_run.json` đủ trường; một bước exit khác 0 thì dừng ở đó, `dry_run.json` vẫn được ghi với `gate = FAIL`.
- Hash ranking khác hash đóng băng thì dừng ở bước 1.
